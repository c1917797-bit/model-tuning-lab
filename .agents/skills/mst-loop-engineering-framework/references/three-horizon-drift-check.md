# Three-horizon drift check

Every task can be checked against three horizons. For a one-step task, a brief
mental or one-line check is enough; do not invent milestones or three separate
documents. Persist the goal map when work spans stages, sessions, or long runs.

Keep a concise goal map in the workstream state:

- **Long term:** the durable user outcome and final acceptance boundary.
- **Medium term:** the current capability or milestone that advances it;
  identify what remains unverified.
- **Short term:** the next falsifiable run or edit, frozen inputs, authorized
  resources and time limit, pass/fail evidence, and stop condition.

At launch, at declared observation checkpoints during a long run, after a
material result or failure, and before a retry or scope change, ask whether
the short action closes a missing medium-term evidence gap and whether that
milestone still serves the long-term objective. Search
for an already verified artifact first; reuse it when its identity matches
instead of rerunning it for a fresh timestamp. If a proposed action no longer
closes a gap, replan and update the handoff.

Record completed, active, and next work with run IDs, evidence locations, and
the remaining acceptance gap. Keep a safe running experiment alive while
checking orientation. A checkpoint distinguishes normal slow progress from a
declared failure signal; it is not a pretext to restart an unchanged job.
Stop only for its declared gate, safety, authority, or resource boundary.
When a result invalidates the current short step (for example, lost isolation),
freeze its evidence, update the short gate, and retain the medium and long
goals unless the user changes them. A successor should be able to choose the
same next action from repository state without relying on chat history.
