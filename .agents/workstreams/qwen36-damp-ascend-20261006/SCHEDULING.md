# Continuous preparation and NPU execution queue

User explicitly authorized parallel agents for one or multiple papers and continuous
resource scheduling on 2026-10-06. Product heartbeat ascend is ACTIVE, every 30
minutes, created anew after the old id was confirmed absent. Actual work remains
subject to app/host connectivity, resources, readiness and numerical gates; no
claim of uninterrupted 24/7 hardware occupation.

- Main agent owns the NPU4-7 execution pool, output paths, shared Git edits and
  checkpoint publication. TP4 paired performance runs never overlap other loads.
- Parallel preparation lane A: current DAMP equations/packing and GQA mapping.
- Parallel preparation lane B: DAMP calibration train data/provenance and bounded
  live capture, no benchmark evaluation leakage.
- Parallel preparation lane C: native/operator reuse, DAMP-specific compressed
  storage ABI and fused update design.
- Completed preparers rotate to the highest-priority next training-free paper
  with insufficient evidence; preparation alone does not start its 24h deadline.
- Every ready packet must state source/revision, mechanism-to-code mapping,
  adaptation gap, independent oracle, multi-step/slot/graph matrix, matched dense
  protocol, outputs that cannot overwrite old evidence, rollback and abort rules.
- Queue states: preparing -> ready for numerical gate -> numerical-pass ->
  matched E2E screen -> final performance/quality -> scoped terminal conclusion.
- Do not fill idle time with repeated deterministic failures, dummy loops or
  irrelevant operator benchmarks. When no safe ready task exists, finish useful
  preparation and report the actual gap.
- Alternative same-host control endpoint mb was freshly proven through topology,
  peer_direct target, hostname, architecture, canonical Git HEAD and NPU/UDA.
  An unavailable ma observation is not a hardware blocker and not permission to
  relaunch a possibly running job.
