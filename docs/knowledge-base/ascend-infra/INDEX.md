## 知识条目的质量契约

一条可用于修改代码的知识至少包含：适用条件；机制与推导；不可改变的语义；可改变的实现边界；最小鉴别实验；反例/失效条件；一手来源或实际证据；未完成项。把来源事实、本文推导、实测结论、假说分别标明。未知不是否定。

新论文的设计备忘录要回答：

1. 当前 checkpoint 的哪个层/阶段满足论文假设？真实 worker 是否执行该路径？
2. 节省的是什么：FLOPs、HBM 字节、launch、通信、重复计算，还是容量？新增成本是什么？
3. 修改哪些文件/接口才能保留该机制？哪些数学、缓存、调度和输出语义不能改？
4. 独立参考如何检测错误？哪项实验能区分算法近似、适配 bug、原生数值和测量问题？
5. 通过短门禁后如何进入整模型？如果失败，什么证据支持修复、另测配置或停止？

不能用年度、论文分数、算子倍数、代码构建成功或知识库审计 PASS 替代这些答案。

## 能力验证，而非背诵

交接者应能独立推导递推和 chunk 表示、解释误差为何累积、给出 DMA/生命周期反例、从关键路径估计机会、设计匹配对照，并对一份未见过的失败帧提出互斥诊断。检查结果看实际适配代码和实验，而非是否复述本库。

维护规则：实质阶段结束后更新相关条目/反例；旧结论用新证据标记 superseded，不覆盖失败；项目数据与大日志不入 Git。本库缺乏证明的地方明确写 pending，不能补写成已经落地。
