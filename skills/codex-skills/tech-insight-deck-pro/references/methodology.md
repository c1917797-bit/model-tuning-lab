## 1. 从决策问题切入

先回答四个问题：

1. 这份洞察支持什么决策？
2. 目标受众需要做出什么取舍？
3. 时间窗口是当前、12–24 个月，还是更长周期？
4. 哪些技术边界必须纳入，哪些明确排除？

方向应按决策维度划分，不要机械采用“硬件 / 软件 / 应用”分类。

## 2. 先形成趋势主线

趋势页不是新闻摘要。先把主题拆成 3–4 个有先后关系的技术阶段，再为每个阶段选择一个能把变化说具体的系统、项目、标准或论文。

每个阶段必须同时包含：

- `stage_id`：供后续方向和论文洞察页引用
- `technical_change`：这一阶段真正改变了什么
- `example`：一个与该变化直接对应的代表性进展

`example` 必须包含机构/团队、日期、可核验的技术事实、原始来源、真实图片和图注。`kind` 只用于内部校验，不显示在页面上。

阶段名称根据主题本身来写。例如端侧 Agent 可用“单模型驻留”“任务级协同”“跨设备调度”，不要机械套用“已验证 / 工程化 / 规模化”。

页面按行组织：

`阶段与技术变化 → 代表性进展（图片、事实、来源）`

读者不需要跨栏匹配材料。底部只用一句 `viewpoint` 收束观点。

`technical_change`、`example.fact`、`viewpoint` 都要写成完整、自然的中文句子，让非专家读者也能顺畅读下去：交代清楚主语和动作，该有的连接词不要省略，不要写成关键词罗列或电报式短语拼接。

## 3. 串联后续技术页

每个方向必须说明它支撑哪个趋势阶段。每个技术页必须写清：

- 当前系统、流程或能力已经做到什么，仍受哪些具体约束
- 这些约束造成的痛点，以及本页技术要解决的问题
- 它验证或挑战了哪条趋势判断
- 论文提供的关键证据是什么
- 证据对产品或技术路线意味着什么

“技术背景”不是技术定义。内部把内容拆为当前状态、痛点和课题问题，是为了保证信息完整，不是为了把“现状：”“痛点：”“问题：”这些标签显示在页面上。最终文案必须是一个连续自然段：先说明对象、场景与当前约束，再承接说明在什么条件下出现什么损失、瓶颈或风险，最后自然引出本页课题需要解决的问题。避免“某技术是一种……”这类百科式开头，也不要手工分行。

使用以下逻辑检查：

`代表性进展 → 技术变化 → 技术阶段 → 方向假设 → 论文机制 → 实验结果 → 洞察观点`

若只能描述论文内容，却无法支撑趋势判断，删除该论文或调整方向。

## 4. 来源与筛选

主要时间窗口为最近 18 个月。基础论文可更早，但必须说明其基础地位。

来源优先级：

1. 论文原文、正式会议/期刊、标准组织
2. 官方研究机构、实验室或厂商技术博客
3. 官方产品文档、开发者大会、开源仓库
4. 高质量行业分析，仅用于补充产业语境

每项技术至少交叉核对三个独立权威来源。不要把同一论文的 arXiv、项目页和转载视为三个独立来源。

筛选维度：

- 决策相关性
- 技术影响力
- 时效性
- 工程成熟度
- 证据可验证性
- 是否有可用的真实架构图和实验图

没有真实图或关键数字无法核验时，不进入单项技术页。

## 5. 技术图片选择与裁切

技术细节区只选 1–2 张与当前机制直接相关的图片：

- 单图适合一张图已经完整说明架构或流程的情况；按原图比例选择“上图下文”或“左图右文”。
- 双图适合两张图分别说明总体架构与关键子机制、训练与推理、系统流程与模块细节等互补关系；两张图固定横向排列，并按原图比例分配宽度。
- 不为填满版面重复同一张图，也不把无关实验图塞入技术细节区。

从论文 PDF 或外部页面截图时：

1. 优先使用论文原图、作者项目页或官方数据源中的高分辨率图片。
2. PDF 渲染使用至少 300 DPI；成图长边至少 1000 px、短边至少 350 px。
3. 保留完整图框、图例、轴标、箭头、节点名称、关键数值和必要图注。
4. 排除页眉页脚、页码、相邻正文段落、参考文献和与本页判断无关的区域。
5. 在 100% 比例下检查文字可读性；放入 PPT 后再检查一次裁切与缩放结果。
6. 在 `figure_quality_checks` 中逐图确认 `complete`、`clean_crop` 和 `legible`。

只允许去掉图像外围的无关页边或空白，不允许用自动居中裁切截断论文图的内容。

## 6. 学术资源洞察

这一页回答“谁在持续做这件事，可以跟谁、跟什么课题继续深入”。

左侧列高校及实验室：

- 高校名称和官方链接
- 学院 / 实验室
- 主要研究方向
- 与本主题最相关的长期积累

右侧列教师与课题：

- 教师姓名、职称、主页
- 所属高校或团队
- 研究方向
- 代表课题、时间和课题链接

只采用高校、实验室、教师主页、基金项目或课题官方页面能够核验的信息。不要把论文标题简单堆成资源清单。

## 7. 技术洞察观点

技术洞察观点必须压缩前文，并用 3 个与主题直接相关的小标题展开。标题应说清技术矛盾或变化，例如“调度从模型级转向任务级”，不要使用通用阶段词。

补充：

- `unresolved`：仍未解决的具体技术问题
- `suggestion`：一条有对象、有动作、有先后顺序的建议

不要重复论文摘要，也不要使用无法执行的泛化表达。

`viewpoint`（压缩前文的一句话观点）、`sections[].points`、`unresolved`、`suggestion` 都要写成完整、自然的中文句子，像是讲给同事听的判断和建议，而不是关键词罗列；每条 `points` 说清一个判断及其理由，不要只写结论性短语。

## 8. 写作规范

- 用具体主语、具体动作、具体数字
- 论文标题与技术术语保留英文，解释和判断使用中文
- 先写结论，再写证据
- 句子短，避免堆砌形容词
- 不使用“近年来”“随着……快速发展”“赋能”“全方位”“值得注意的是”等套话
- 不把研究方法写成页面文案；避免“证据依据”“业界实践”“最新论文”“研究集群”“证据缺口”“阅读策略”“核心判断”“置信度”等标签
- 小标题优先使用主题中的技术名词、系统动作和约束条件
- 所有随时间变化的事实与数量必须联网核验

技术细节、实验方法、实验结果三个区域都遵循「先总起、再分点、每点标签加粗」的写法，不要写成一段不分点的介绍：

- 技术细节先写 `tech_detail_summary`（核心思想）：用一整句适合人读的话说清楚这项技术解决了什么问题、整体思路是什么，可以比分点略长，写成完整、自然的中文句子，而不是名词堆砌的电报体；这句话本身不含冒号标签，加粗的“核心思想：”前缀由脚本自动加上。再写 `tech_detail_points`（关键技术）：2–3 个「关键技术名称：简述」的分点，技术名称直接对应论文里的模块或机制名称（如“动态稀疏注意力”“分层 KV 缓存”），会自动加粗显示，不要用“机制”“设计”“边界”这类空泛标签代替真实技术名称；简述部分也要写成一句通顺的话，让非该领域的读者也能读懂在做什么、为什么有效。
- 实验方法按「实验设计 → 平台与基线 → 数据与变量」从整体到细节展开，体现层次感：先说验证目标，再说运行平台与对照基线，最后说具体数据规模或受控变量；不要把目的和配置细节混在同一条里；每条也要写成通顺的一句话，不要只堆参数名和数值。
- 实验结果同样先写 `experiment_result_summary`（实验总结）：一整句适合人读的话说清楚这组实验总体证明了什么，可以比分点略长，写成完整、自然的中文句子；这句话本身不含冒号标签，加粗的“实验总结：”前缀由脚本自动加上。再写 `experiment_result_points`（关键指标）：2–3 条，每条都必须以具体指标名称开头（如吞吐量、延迟、显存占用、准确率），不要写“关键数据”“实验数据”这类占位词，也不要再重复“实验结果”这几个字——模板里这一区域本身已经带有“实验结果”标签；指标名称后直接写带数字或百分比的结果表现，写成通顺的一句话。

以上写法不只适用于单项技术页：技术趋势洞察页的 `technical_change`/`fact`/`viewpoint`、洞察摘要页的方向总结、技术洞察观点页的 `viewpoint`/`points`/`unresolved`/`suggestion`，全部都要照顾人类读者的阅读体验——宁可稍微多写几个字把话说完整、说自然，也不要为了塞进版面预算或显得“专业”而写成生硬的短语拼接；同一句里该有的主谓宾、该有的连接词都不要省略。

每段完成后检查：资深工程师是否会用同样方式表达；若不会，重写。

## 9. 版面容量与洞察启示

单项技术页的技术背景、技术细节、实验方法与结果和洞察启示都使用固定模板区域。先按
`content-schema.md` 的版面预算写作，再运行 `validate_spec.py`；生成后运行
`check_ppt_text_overflow.ps1` 测量 PowerPoint 实际文本边界。

文字超量时按以下顺序处理：

1. 删除重复结论、修饰语和论文摘要式铺垫。
2. 每个要点只保留一个机制、一组条件和一个结果。
3. 把次要信息留在 Markdown/HTML 预览或来源中。
4. 仍放不下时重新组织内容，不缩小模板字号、不压缩行距、不裁切文字。

洞察启示不是机制复述，也不是口号。用一段简明的话说清楚三件事：

`先进性（相比现有方案或基线，具体强在哪里） → 成熟度（研究原型、小规模验证，还是可规模化落地） → 借鉴意义（对当前系统或工程实践有什么具体指导）`

至少用 70 个中文字符讲完这三点即可，不必再复述机制细节或实验过程；避免只有“性能更好”
“值得关注”或“建议持续跟踪”等浅层结论，也不要堆砌形容词把三点拆成长段落。

“关键技术”“关键指标”分点还有一条额外的物理约束：每一条分点在渲染时都是独立段落，
无论文字多短都会独占一行，不会和上一条共享半行空间。因此“单项上限”（34 个版面单位）
是按“能在模板一行内排完”反推出来的，不是随意收紧；写这两类分点时，宁可少写一个从句，
也不要让单条内容超过一行的物理容量，否则该条会挤占下一行、把总高度顶穿模板卡片下边框。
`build_deck.py` 会在实验图/技术图比预留空间矮时，把多出的高度动态让给下方文字（详见
`content-schema.md` 的版面预算说明），但这只能补偿“图片留白”，补不了“分点本身写得
太长”，所以分点长度仍要按一行的上限来写。

## 10. 模板一致性

模板一致不等于“色值接近”。页面必须实际继承 `assets/template.pptx` 的页面尺寸、母版、
版式和结构形状。最终文件只由 `scripts/build_deck.py` 写出。

单项洞察、趋势、学术资源和技术洞察观点页都从模板第 4 页复制。保留红色标题、虚线圆角双栏、
灰色背景带、底部观点带及母版页脚；只替换正文占位内容和双栏内部布局。

演示工具可以用于只读导入、逐页渲染和检查，但不得用 `Presentation.create` 或空白页重画，
也不得把检查后的演示文稿重新导出为“最终版”。生成后运行
`validate_template_fidelity.py`；任何母版、版式、页面尺寸或关键结构差异都视为失败。
