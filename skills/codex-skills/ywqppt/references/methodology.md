# 技术洞察方法论

本文件定义如何为本 skill 输出**真正有业务价值**的技术洞察内容。
按顺序执行：先定调研课题 → 拉信息 → 选技术 → 写每页 → 出图。

---

## 1. 课题理解与方向归类

收到课题后，先**不要急着搜**。先回答三个问题：

1. **业务侧关心什么？** 课题背后是要解决什么问题、做什么决策？（例如"评估是否要自研编译器"和"评估是否要采购 Groq 卡"调研策略完全不同）
2. **课题的技术外延是什么？** 哪些子领域必然相关？（例如"Groq 编译器"会牵出：Groq 硬件架构、TSP/SRAM 内存模型、AOT 编译、vLLM/TensorRT-LLM 等竞品的编译器、MLIR 生态）
3. **方向应该怎么切？** 把外延归并成 **≤3 个方向**。方向之间要互斥、合起来覆盖课题，且每个方向要单独"撑得起一段总结"。

> **不要**机械按"硬件/软件/应用"切，那是 AI 味的归类。
> **应该**按"业务关心的决策维度"切，例如：
> - "对外宣传的性能优势是否站得住"
> - "迁移现有模型的工程成本"
> - "未来 12-24 个月编译器栈的演进路径"

## 2. 检索（多源、去重、按时效与权威加权）

**主要来源**（按权重）：

| 来源 | 权重 | 说明 |
|------|------|------|
| arXiv | 高 | 重点看最近 18 个月 cs.AR / cs.LG / cs.DC，关注 ≥30 引用 或 顶会接收的论文 |
| IEEE Xplore | 高 | ISCA / MICRO / HPCA / ASPLOS / DAC 近两届 |
| ACM DL | 高 | OSDI / SOSP / PLDI / NeurIPS / ICML 近两届 |
| 厂商技术博客 | 中-高 | NVIDIA Developer / Google Research / Meta AI / Microsoft Research / 字节火山 / 阿里巴巴达摩 / 腾讯 AI Lab / 华为诺亚 / 三星 SAIT |
| 标准与白皮书 | 中 | MLPerf, OCP, ONNX, MLIR community |
| 产品发布 / 开发者大会 | 中 | GTC, Hot Chips, Computex, OCP Summit |
| 高质量分析媒体 | 低-中 | SemiAnalysis, The Information, EE Times |

**主要玩家追踪清单**（每次洞察都问一遍"这家在这事上做了什么"）：

> 谷歌 / Meta / 微软 / 字节跳动 / 腾讯 / 快手 / 阿里 / 苹果 / 三星 / 英伟达 / AMD / 英特尔 / 华为 / 高通 / 特斯拉 / OpenAI / Anthropic / DeepMind

如果某玩家在该方向**没有公开动作**，也是有价值的信号，写在洞察启示里。

**搜索策略**：

- 用 web_search 工具至少检索 **3 个不同来源**，不要全是 arXiv 也不要全是博客
- 时间窗口：**最近 18 个月**为主；早于此的论文只在它是"基础性引用"时纳入（如 attention is all you need、Megatron 这类）
- 至少检索一遍英文，必要时再用中文搜——中文资料覆盖国内厂商动作更全

## 3. 技术筛选（每方向 ≤5 个）

候选很多，但每方向最终只入选 **≤5 个技术**。打分维度（每项 1-5 分，总分排序）：

1. **来源热度**：论文引用数 / GitHub star / 媒体报道密度
2. **业务价值**：能不能直接对应到产品决策？是不是处在工程化前夜？
3. **技术影响力**：是不是改变行业默认做法的工作？还是渐进改良？
4. **时效性**：近 18 个月内有显著进展？
5. **可证实性**：有没有可截图的实验结果或系统图？没有就剔除——**这页 PPT 没图就不成立**。

> 宁可一个方向只写 2 个高质量技术，也不要凑满 5 个。

## 4. 每个技术页的写作（对应 slide 4 的 6 块）

每页都是同一个结构。按这个顺序写：

### 4.1 Title（顶部）

格式：**论文/技术原标题（保留英文）**。例如：
- ✅ `Agent.xpu: Efficient Scheduling of Agentic LLM Workloads on Heterogeneous SoC`
- ❌ `异构 SoC 上的高效智能体大模型调度方案`

### 4.2 参考来源（标题下面红字小字）

格式：`参考： <来源标识>`。常见形式：
- `arXiv:2506.24045 v2`
- `ISCA 2024, doi:10.1109/ISCA59077.2024.00050`
- `Google Research Blog, 2025-03-12`
- `NVIDIA GTC 2025 Keynote`

### 4.3 技术背景（左上 灰底"技术背景"标签 + 一段话）

**80-120 字**。回答：谁做的 + 解决什么问题 + 总体路径。
不要写"近年来 XX 越来越重要……"这种 AI 开场。**直接进入主语 + 谓语**。

✅ `Agent.xpu 是由北京大学和香港大学的研究团队开发的首个专门针对异构 SoC 设计的并发式 LLM 推理引擎，目标是解决端侧 Agent 同时跑响应式与主动式任务时的延迟与效率问题。`

❌ `随着大模型的快速发展，端侧推理变得越来越重要。本文提出……`

### 4.4 技术细节（左侧）

**上半**：论文中的**系统设计图原图**（必须！没图就别选这篇）。一般是论文 Figure 1 或 Figure 7 的 system overview / pipeline / architecture。

**下半**：3 条要点，每条 1-2 行。**每条以加粗的关键词起手**：
```
离线构建异构执行图（HEG）：将 LLM 算子按亲和性拆分……
在线 Kernel 级抢占调度：Reactive 任务到达时可在 kernel 边界精准打断……
带宽感知 NPU-iGPU 协同：实时检测 DDR 总线饱和状态，动态路由计算 kernel……
```

### 4.5 实验结果（右侧）

**上**：实验方法。3 行：平台与模型 / 负载模拟 / 对比基准。

**中**：论文中的**实验结果图原图**（必须！）。通常是 throughput/latency 柱状图、energy 对比图、scaling 曲线。

**下**：2 条核心结论，**带具体数字**。
- ✅ `性能：主动式任务吞吐量提升 1.2-4.9 倍，响应式任务延迟（P90）降低 91% 以上。`
- ❌ `性能：相比基线方案有显著提升。`

### 4.6 洞察启示（底部 灰底"洞察启示"标签 + 一段话）

**60-100 字**。**这是整页最重要的一块**——它直接对应业务决策。

回答："如果这条技术成立，对我们的产品/战略意味着什么？"

✅ `通过异构芯片的高度协同，无需昂贵的云端算力即可支持复杂的多 Agent 协程流，在保障用户数据绝对私密的同时，可大幅降低推理成本。`

❌ `这是一个有趣的工作，对未来端侧 AI 发展有借鉴意义。`（这就是 AI 味）

## 5. 摘要页（slide 2）写作

**方向总结（每个 ≤130 字）**：必须有立场和判断，不能只是描述。

✅ `方向 1：Groq 的核心壁垒在编译器而非硅片。其 TSP 架构把所有调度决策推到编译期，运行时是确定性的——这意味着真正的护城河是 8 年积累的编译器代码量与团队，而非可被复制的 ASIC 设计。短期内难以被对手追平，但这条路也限制了它支持新算子结构的灵活性。`

❌ `方向 1：Groq 是一家做 AI 芯片的公司，使用了独特的 TSP 架构。它的编译器很重要。`

**整体总结（≤80 字）**：用一句话回答"如果只能记一句，是哪句"。

✅ `Groq 走的是"用编译器复杂度换运行时确定性"的极端路线，对推理服务 SLA 友好但对模型快速迭代不友好；当前阶段适合作为补充推理通道而非主力。`

## 6. 文风规则（避免 AI 味）

**禁忌词**——出现就改：
- "近年来"、"随着……的快速发展"、"在当今 AI 时代"
- "总的来说"、"综上所述"、"值得注意的是"
- "赋能"、"加持"、"全方位"、"一站式"
- "本文"、"我们"（论文里的"我们"在你转述时要改成具体主语）
- "进一步"、"更加"（删掉，多半冗余）

**句式偏好**：
- 短句优先，**主谓宾干净**
- 数字要具体（"提升 91%" 优于 "显著提升"）
- 转述论文时，主语要具体到团队或机构（"北大-港大团队……"）而不是"该工作……"
- 用业务行话，不用论文行话（"工程化前夜" 优于 "具备较强可行性"）

**核对自查**：每段读一遍，问自己——"如果是一个有 8 年经验的资深工程师在写这段，他会这么写吗？"如果不会，重写。
